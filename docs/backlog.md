| TC-14 | `EventSocket::recv` published events outside the receive lock | P1 | S | done | Codex review on [#69](https://github.com/VitalyVorobyev/viva-genicam/pull/69). #68's recheck-after-locking fix left a few instructions of window: the decoded datagram's first event was returned and the remainder queued *after* the receive lock was released, so a second consumer could take the lock, find the queue empty and block in `recv_from` on a device that had already finished speaking. | TC-08 | Reconcile packet-size accounting | P1 | S | done | `best_packet_size` subtracted 42 (incl. | TC-15 | `StatusCode::from_raw` mislabels three codes and cannot name a fourth | P0 | M | planned | **Found via hardware**: #45's FLIR BFS-PGE-31S4C returned `0x8006` on a register write and the user saw `device reported status Unknown(32774)`. `crates/viva-gencp/src/lib.rs:99-122` maps `0x8004`→`DeviceBusy` (really `WRITE_PROTECT`), `0x8005`→`Error` (really `BAD_ALIGNMENT`), and has no entry for `0x8006` (`ACCESS_DENIED`), `0x8007` (`BUSY`) or `0x8FFF` (the actual generic error). So a write-protected register reports "device busy". Corroborated by two independent sources that agree completely: Wireshark `epan/dissectors/packet-gvcp.c:204-229` (`GEV_STATUS_*`, with deprecation and GEV-version annotations) and aravis `arvgvcpprivate.h:183-205` / `arvuvcpprivate.h:116-135`. **Check against the spec before landing** — neither source is authority. | TC-16 | One flat `StatusCode` cannot serve both GVCP and GenCP | P0 | M | planned | The tables share `0x0000`, `0x8001`-`0x8007` and `0x8FFF`, then **conflict at the same code**: `0x800B` is `NO_MSG` (deprecated) in GVCP but `MSG_TIMEOUT` in GenCP. GVCP additionally owns the packet-resend family (`0x0100`, `0x800C`-`0x8017`); GenCP owns `0xA001`-`0xA101`. So adding entries cannot make the shared enum correct — it needs a shared core plus per-transport extension. **Write an ADR.** This also corrects TC-01: `viva-u3v/src/control.rs:29` treats status `0x8006` as `PENDING_ACK`, so a denied U3V write is retried 100× (`MAX_PENDING_RETRIES`) and surfaces as a pending-ack failure, while a real pending-ack — command id `0x0805` — is never recognised and slow U3V devices time out. The test at `control.rs:472` asserts the misreading back to us: fourth occurrence of the TC-04 pattern. **Couples to TC-15** — fixing `from_raw` makes the `Unknown(0x8006)` arm dead code, so they land together |
| TC-10 | `viva-gencp::encode_cmd` is dead *and* divergent | P2 | S | planned | It writes a different header shape than `viva-gige` actually uses and has no callers outside its own tests (`crates/viva-gencp/src/lib.rs:179-188`) |
