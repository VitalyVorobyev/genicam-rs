| TC-15 | `StatusCode::from_raw` mislabels three codes and cannot name a fourth | P0 | M | done | **Found via hardware**: #45's FLIR BFS-PGE-31S4C returned `0x8006` on a register write and the user saw `device reported status Unknown(32774)`. `crates/viva-gencp/src/lib.rs:99-122` maps `0x8004`→`DeviceBusy` (really `WRITE_PROTECT`), `0x8005`→`Error` (really `BAD_ALIGNMENT`), and has no entry for `0x8006` (`ACCESS_DENIED`), `0x8007` (`BUSY`) or `0x8FFF` (the actual generic error). So a write-protected register reports "device busy". Corroborated by two independent sources that agree completely: Wireshark `epan/dissectors/packet-gvcp.c:204-229` (`GEV_STATUS_*`, with deprecation and GEV-version annotations) and aravis `arvgvcpprivate.h:183-205` / `arvuvcpprivate.h:116-135`. **Check against the spec before landing** — neither source is authority. Replaced by `StatusCode::is_retryable()`, with UDP-device tests asserting the device sees two commands for BUSY and one for WRITE_PROTECT. Spec check still outstanding: the values rest on Wireshark + aravis |
| TC-16 | One flat `StatusCode` cannot serve both GVCP and GenCP | P0 | M | in-progress | The tables share `0x0000`, `0x8001`-`0x8007` and `0x8FFF`, then **conflict at the same code**: `0x800B` is `NO_MSG` (deprecated) in GVCP but `MSG_TIMEOUT` in GenCP. GVCP additionally owns the packet-resend family (`0x0100`, `0x800C`-`0x8017`); GenCP owns `0xA001`-`0xA101`. So adding entries cannot make the shared enum correct — it needs a shared core plus per-transport extension. **Write an ADR.** This also corrects TC-01, and the U3V half is worse than "unrecognised" — it is **silent wrong data**. `decode_ack` reads the acknowledgement's command id into `let _opcode` and discards it (`viva-u3v/src/control.rs:267`), and `transact` validates only `request_id` (`:180`). A GenCP pending-ack is a distinct command (`0x0805`) carrying `time_to_completion` in its SCD, with a *success* status — so on a device that uses one we accept it as the real answer and **return the timeout bytes as the register value**. A 4-byte `ReadRegister` gets a plausible-looking wrong number. Meanwhile `StatusCode::Unknown(0x8006)` (`:29`, `:189`) only ever fires on a genuine `ACCESS_DENIED`, which we then sleep-and-retry 100× (`MAX_PENDING_RETRIES`) before reporting `Timeout` instead of "access denied". Both halves wrong, mutually reinforcing. aravis gets this right and shows the shape of the fix (`arvuvdevice.c:344-373`): read status *and* command id, test `command == PENDING_ACK` first and independent of status, then require `command == expected_ack_command` before accepting the payload — we already have `OpCode::ack_code()` for that comparison. The test at `control.rs:472` asserts the misreading back to us: fourth occurrence of the TC-04 pattern. **Couples to TC-15** — fixing `from_raw` makes the `Unknown(0x8006)` arm dead code, so they landed together. **Done so far:** pending-ack is keyed off command id `0x0805` (`viva_gencp::PENDING_ACK_COMMAND`), `decode_ack` keeps the command id, `transact` requires it to equal `OpCode::ack_code()` before accepting a payload, and the SCD timeout is read as a little-endian `u16` at offset 2 — the old big-endian `u32` read turned a 1 000 ms request into 59 395 ms. `build_ack` now takes an explicit command id, deleting the "opcode doesn't matter for most tests" comment that was the assumption behind the whole defect. **Remaining:** the per-transport wrapper types (ADR-0020 points 1-2). Until they land a transport-specific code decodes as `Unknown(raw)` — reportable but unnamed; `0x800B` is the forcing case and no current code path decodes it, so this is safe to defer to the 0.4.0 window beside API-02/API-03 |
